ARCHITECTURE OVERVIEW

KnowledgeBase 不是一个“文档搜索工具”，而是一套让 Agent 先找依据、再做判断的知识底座。

它解决的不是“资料能不能搜到”，而是“专业问题能不能基于证据稳定回答、持续积累、复用给更多专业能力”。这决定了它不是一次性功能，而是一层长期可运营的基础设施。

可追溯

一句话理解：我们做的不是“让模型多看几篇文档”，而是“让 Agent 在专业领域有一套稳定、可追溯、可运营的证据系统”。

当前已打通

知识沉淀、证据检索、Agent 消费这三层主链。

当前真实样例

基于云库中的 5G 核心网真实文档，完成从知识入库到证据回答的完整闭环。

当前工程边界

已经有发布边界、生效版本和独立智能服务层运行面，不是临时拼装型能力。

目标态方向

从单点问答能力，走向多个专业 Skill 共享的知识基础设施。

SECTION 01

为什么需要知识后端

大模型进入专业场景后，真正的瓶颈往往不是语言能力，而是知识依据、风险边界和长期运营能力。

传统文档搜索的局限

  • 只看关键词，容易错过表达不同但语义一致的专业知识。
  • 段落、表格、步骤和上下文关系往往被打散，资料能搜到，但不容易直接用。
  • 新旧内容混在一起时，很难判断当前应该信哪一版、用哪一份。

Agent 时代对知识服务的要求

  • 不是返回“相关文档”，而是理解当前问题要概念解释、结构说明还是进一步判断。
  • 不是返回零散片段，而是返回带来源、上下文和关系的证据包。
  • 不是一次问一次搜，而是形成可持续更新、持续沉淀、持续复用的知识体系。
KnowledgeBase 的定位：知识加工（Mining）+ 精准检索（Serving）+ 智能服务层三位一体的 Agent Knowledge Backend。它不是给人直接使用的搜索引擎，而是给智能体使用的知识服务底座。
SECTION 02

设计哲学

这套系统不是从“做一个问答功能”出发，而是从长期可运营的知识系统出发。原版里的很多设计思想仍然成立，只是在当前阶段先按能落地的边界逐步实现。

设计决策核心思想实际意义
内容快照不可变同一内容视为同一份知识快照保证知识边界清晰，便于复用、比对、回滚，而不是每次更新都重新堆一份。
读写路径分离知识生产和知识消费拆开后台整理知识，不会干扰在线使用；在线取证稳定读取生效知识。
阶段过程可回溯每一步知识变化都留痕出了问题知道卡在哪一步，也便于后续做质量治理和运营分析。
知识分层组织概念、机制、方法、条件、场景不混在一起不同问题可以拿到不同粒度的知识，不会所有内容都挤成一个平面文档库。
关系与溯源并重既关心知识之间怎么关联，也关心结论从哪来回答不只“像是合理”，还能够回到文档依据和上下文来源。
知识持续演进知识体系会持续积累、持续替换、持续优化这决定它是基础设施，而不是一次性交付的问答功能。
SECTION 03

整体系统架构

KnowledgeBase 当前已经不是单进程里的一个”搜索模块”，而是三个可独立演进的运行面。这样做的目的，是把知识生产、知识消费和智能服务层拆开，避免后续所有复杂度都堆在一个点上。

角色当前职责拆分后的意义
Mining 把文档整理成结构化知识，形成可发布、可替换、可持续积累的知识资产。 知识生产是后台工作，不能与在线问答耦合，否则无法稳定运营。
Serving 面对问题按需取证，返回证据包，支撑 Agent 做下一步判断。 在线取证要求低延迟、稳定读，不应该被知识加工过程干扰。
智能服务层 统一管理智能服务能力，承担模板治理、同步调用、异步任务和审计追踪。 把智能服务层独立出来，后续才能单独治理质量、成本、SLA 和运营能力。

这套架构带来的直接结果

  • 后续扩知识时，不会影响在线使用。
  • 后续扩更多 Skill 时，不需要重做知识底座。
  • 后续增强模型能力时，不会反向污染知识主链。

这套架构体现出的平台边界

  • 不是单个搜索模块，而是可独立演进的三层运行面。
  • 不是为了一个问题入口，而是为了多类专业能力共用。
  • 不是一次性接文档，而是为长期演进预留了明确骨架。

SECTION 05

当前进展

当前已经不是停留在概念或单点验证阶段，而是把知识生产、在线取证、版本生效和智能服务层的主干链路打通了。这里保留少量技术信息，用来说明工作深度，但不展开到代码层面。

能力面当前状态已经证明的能力
知识摄入 文档进入统一知识面，而不是临时塞进上下文窗口。 已经具备持续导入和持续沉淀基础。
知识结构化 系统会识别章节、段落、表格、列表，并保留结构角色和上下文边界。 回答不再只依赖文本片段，而是可以利用文档结构。
检索主链 已经形成理解问题、多路取证、融合整理和证据输出的在线主链。 不是单路搜索，而是有路由和融合策略的在线取证链。
证据输出 输出的是带来源、上下文与关联关系的证据包，而不是单一命中文档。 Agent 能基于证据判断能不能答，而不是只拿到片段自己拼。
版本边界 知识形成后要经过构建 / 发布才能进入在线读取面。 知识更新和在线服务解耦，具备工程化运营基础。
智能服务层 智能服务层已形成独立运行面，既支持在线使用，也支持后台增强。 后续可以单独治理质量、成本与审计，而不是把模型能力散在各模块中。
场景包 当前已经有 `generic`、`cloud_core_network` 等独立 YAML 场景配置包，既定义领域规则，也定义检索和处理策略。 说明这不是一条写死的知识链，而是开始具备跨场景复用和迁移能力。
可拼装处理链 YAML 不只是参数表，还承载语义角色映射、抽取规则、路径策略、评测问题和阶段定制点；代码里也已经有阶段注册机制作为热插拔雏形。 目标不是维护一条固定处理链，而是按场景组合不同阶段，形成更通用的平台能力。

当前实现的重点不是“算法多”，而是“边界清”

  • 知识生产和在线取证已经拆开。
  • 在线取证和智能服务层已经拆开。
  • 中间过程和生效版本已经拆开。
  • 基础能力和领域场景也已经开始拆开。

这也是当前工作量所在

  • 不是只把文档喂进库里，而是把知识做成可发布对象。
  • 不是只给检索结果，而是把结果变成可供 Agent 决策的证据包。
  • 不是只做调用模型，而是给模型使用建立了独立运行与治理面。
  • 不是只适配一个场景，而是在把场景差异收敛到场景包与可拼装阶段中。
场景包的意义：当前代码里，知识挖掘和在线取证都已经开始读取各自的 YAML 场景配置包。它既能定义领域词表、语义规则、检索权重，也能承接不同阶段的定制化策略。往前走一步，主链就可以从“按代码写死”演进到“按场景装配”，这也是泛化能力的关键。

业务感知不只是“看懂流量是什么”。它的第一步确实是识别用户会话中的业务类型，但识别只是基础。识别完成后，网络会把不同业务映射到不同的控制和运营动作，例如带宽管理、QoS 策略、重定向，以及在线、离线、融合计费。也就是说，它把“识别结果”进一步转化为“资源控制”和“计费运营”的执行能力，所以本质上是一套面向运营的综合能力，而不是单纯的识别技术。

这正是和一般方案的差异：系统不是把几段文本扔给模型，而是先明确“证据够不够”，再基于证据组织回答。

SECTION 07

一条数据的完整旅程

以下例子来自当前知识库中的真实文档 5G核心网架构概述.md。这里适度保留技术细节，但只保留那些真正能帮助理解“我们做了多少事”的内容。

追踪对象：云数据库中的真实文档 5G核心网架构概述.md，当前生效版本中已经形成 15 个原始知识段 与 29 个检索单元。这不是概念例子，而是当前系统里真实存在的一条知识资产链。
01

资料进入知识体系

系统首先识别文档身份、来源和内容边界，把这份 Markdown 文档纳入统一知识面，而不是把它当一段临时上下文直接喂给模型。

02

把文档拆成可理解的知识单元

系统识别章节、段落、表格、列表和它们的关系。这份文档最终形成 15 个结构化知识段，其中既有概念说明，也有表格映射和参考规范。

服务化架构（SBA） 关键网络功能（NF） CUPS 4G→5GC 映射
03

补齐结构语义，而不篡改原文

系统会为知识段补充角色、章节归属、表格结构等信息，并按需生成可问答问题。这里的重点不是“改写内容”，而是让知识更适合被检索和解释。

04

生成可被取证的证据单元

这份文档当前实际生成了 15 个文本型检索单元和 14 个问句型检索单元，便于系统同时回答“定义是什么”与“用户可能怎么问”两类问题。

05

进入发布视图，供在线读取

文档不会在处理中间态被在线读取，而是先进入构建，再进入发布，最后由在线取证链只读取当前生效版本。这一步是工程化边界的关键。

SECTION 08

生效版本：决定当前在线服务到底读哪一个知识视图。

为什么这一层重要

  • 保证在线取证读取的是“已生效知识”，而不是处理中间态。
  • 支持知识的增量更新，而不是每次重做全量导入。
  • 支持版本切换与回滚，降低知识运营风险。

这部分体现出的工程能力

  • 不是简单建库，而是把知识做成了可发布对象。
  • 不是临时更新，而是有明确的变更语义。
  • 不是只管“能用”，而是开始具备“可运维、可治理”的基础。

SECTION 09

当前态 vs 目标态

如果只看表面，像是在做“专业知识问答”。但真正的差异，不在搜索本身，而在把知识变成可运营、可协同、可决策的证据体系。

价值一：让回答更稳

不再依赖模型“像是知道”，而是把专业输出建立在证据之上。对专业领域来说，稳定性本身就是核心价值。

价值二：让结果可追溯

不只是“答没答对”，还要知道“依据来自哪里”。KnowledgeBase 让这一点天然成立。

价值三：让知识可持续积累

新资料不是临时喂给模型，而是进入统一知识体系，形成长期可复用资产。

三层创新，不是单点问答创新
创新 1

从“文档库”升级成“证据底座”

普通方案做到“搜到内容”就结束。我们进一步解决的是：这份内容够不够回答、还缺什么、下一步该怎么做。

创新 2

从“单次问答”升级成“可运营知识资产”

壁垒不在一次答得多好，而在知识能否持续更新、持续治理、持续发布，并稳定供 Agent 使用。

创新 3

从“一个助手”升级成“多个 Skill 共用底座”

KnowledgeBase 的未来不是只服务一个入口，而是支撑配置解释、故障分析、影响判断等多个专业 Skill 协同工作。

SECTION 10

目标态演进方向

目标态必须讲清楚，否则这件事会被误解成“做了一个专业版搜索”。我们的目标不是停留在问答，而是形成专业领域 Agent 的通用知识基础设施。

目标态架构认知
KnowledgeBase
产出标准化证据包
→
智能体调度层
判断该回答、追问还是转交
→
Domain Skills
配置 / 排障 / 解释 / 对比等专业能力组件

最终使用形态：Knowledge Skill Protocol

最终不是把问题直接扔给一个搜索接口，而是形成一套稳定的协同协议：KnowledgeBase 负责产出证据，Agent 负责做动作判断，专业 Skill 负责执行更具体的领域工作。

层级职责目标态要求
KnowledgeBase理解问题、检索证据、返回结构化证据包。来源、上下文、关系、缺口提示都要标准化。
智能体调度层判断证据是否足够，决定回答、追问、谨慎回答还是转交。形成统一的动作决策边界，而不是每个 Skill 各自处理。
Domain Skills消费证据包，执行配置解释、故障分析、影响判断等专业工作。高风险输出必须绑定上游证据，而不是脱离证据自由生成。

目标一：证据驱动成为默认工作方式

任何专业问题，Agent 都不是先答，而是先判断是否需要取证；拿到证据后，再决定回答、追问、谨慎回答或转交下游能力。

目标二：知识底座成为可持续运营的系统

知识持续进入、持续更新、持续发布、持续替换，形成企业级知识运营闭环，而不是一次性导入一批文档后长期失效。

目标三：一套底座支撑多个专业 Skill

每新增一个专业 Skill，复用的不是零，而是同一套已沉淀的证据体系、知识边界和判断规则。

目标态创新栈
创新栈 1

分层知识模型

把概念、机制、方法、条件、场景分层组织，避免所有知识都堆成一个平面集合。这样不同角色和不同 Skill 可以拿到不同粒度的信息。

创新栈 2

关系与溯源分层

未来不仅要知道“哪些知识相关”，还要知道“这些关系怎么来的、证据链在哪里”，把推理和溯源同时做强。

创新栈 3

声明式取证能力

不是每次都手写复杂流程，而是让系统逐步具备更高层次的查询规划与自动组合能力。

创新栈 4

知识自治演化

高质量知识持续积累，低质量知识持续被压制或淘汰，使知识体系不是越堆越乱，而是越用越准。

创新栈 5

可信度评估

未来不仅要给结果，还要逐步给出来源质量、跨源一致性、时效性等维度的可信度判断。

创新栈 6

多 Skill 协同协议

最终不是一个问答系统，而是一套知识协议层，支撑配置、排障、解释、影响分析等多个专业能力共用同一知识底座。

真正的壁垒：难点不在“把资料搜出来”，而在“让 Agent 知道什么时候能答、什么时候不能答”，以及“让知识成为长期可运营、可复用、可协同的基础设施”。这才是和通用方案真正拉开差距的地方。
