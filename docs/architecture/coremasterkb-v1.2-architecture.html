v1.2 TARGET

KnowledgeBase 技术架构

面向 Agent 的知识后端 — 不是文档搜索工具，而是一套可被 Agent 作为 Skill 调用的知识加工、精准检索与自主演化基础设施。 从原始文档摄入，到结构化知识提取，再到意图驱动的混合检索，最终输出可被 Agent 直接消费的 ContextPack。

SECTION 01

为什么需要知识后端

传统文档搜索的局限

  • 关键词盲区：用户问"UPF 怎么处理计费策略"，但文档写的是"用户面功能执行 Charging Rule"，纯关键词匹配直接丢失
  • 无结构理解：表格里的参数对照、流程步骤的先后依赖、段落之间的因果/对比关系，全部丢失
  • 静态不演化：知识只增不减，过时内容和新内容混在一起，无置信度评估，无冲突检测

Agent 时代对知识服务的三个要求

  • 精准意图理解：不是返回"相关文档"，而是理解 Agent 要"概念解释"还是"操作步骤"还是"参数对比"，返回精准 Evidence
  • 结构化证据包：不是一堆零散片段，而是带溯源链、带关系图、带置信度的完整 ContextPack
  • 持续自治演化：知识库能够自动积累高质量内容、淘汰过时内容、检测矛盾内容，越用越准
KnowledgeBase 的定位：知识加工（Mining）+ 精准检索（Serving）+ 智能增强（LLM Runtime）三位一体的 Agent Knowledge Backend。不是给人类用的搜索引擎，而是给 Agent 用的 Skill 级知识服务。
SECTION 02

设计哲学

不是从零造轮子，而是将工业级数据工程实践融入知识系统设计，每个决策解决一个真实痛点。

设计决策工程范式解决的问题
内容快照不可变内容寻址存储相同内容通过 SHA256 哈希去重，一份快照可被多文档引用。文档身份与内容物理分离，避免重复存储
读写路径分离CQRSMining 独占写路径，Serving 纯读路径，通过 Build/Release 边界解耦。写操作永远不会阻塞读服务
阶段事件溯源Event Sourcing每个 Pipeline 阶段产出带时间戳的事件记录，任意文档的处理历史、耗时、失败原因可精确回溯
五层本体组织Hierarchical Ontology概念→机制→方法→条件→场景五层结构，每层对应独立认知框架，不同角色获取不同粒度的知识
双层图分离Dual-Layer Graph推理层（聚合语义边）与溯源层（Fact→Document 证据链）分离，图遍历和证据追溯互不干扰
声明式查询引擎Algebraic Primitivesseed / expand / combine / aggregate / project 五个代数原语，规划器自动检测依赖并行执行
五维置信度评分Multi-Factor Confidence来源权威度×提取方法×本体契合度×跨源一致性×时效性，每条知识都有可信度量化评估
知识自治演化Auto-Promote三层候选词治理 + 自动晋升门控。高质量知识自动积累到本体，低质量被淘汰，实现"自然选择"
SECTION 03

整体系统架构

三大子系统：Mining（知识生产）、Serving（知识消费）、LLM Runtime（智能增强）。这一层只讲三者之间的协作关系，不下沉到单个算法节点。

角色当前实现职责与其他角色的关系
Mining 扫描文档、解析结构、切分 segments、生成 retrieval units、组装 build、激活 release。当前知识主数据面已迁到 PostgreSQL。 向 Serving 发布 active release；按需调用 LLM Runtime 做 enrich、question、discourse 等增强。
Serving 只读 active release，对查询做 understanding、route plan、多路召回、融合、重排和 ContextPack 组装。 不写知识资产；从 Mining 的发布结果读取；在线同步调用 LLM Runtime。
LLM Runtime 独立 FastAPI 服务，提供 /api/v1/tasks、/api/v1/execute、模板管理、幂等、重试、审计链。 不持有知识主数据；为 Mining 提供异步能力，为 Serving 提供同步能力。
当前口径：KnowledgeBase 的核心不是把所有能力塞进一个进程，而是把“知识生产”“知识消费”“智能增强”拆成三个可独立演进的运行面。
面向 Agent 的最终定位：KnowledgeBase 不是“直接替 Agent 回答问题”的万能助手，而是一个可被 Skill 调用的证据底座。Agent 先通过 Serving 取回证据包，再决定直接回答、先追问、谨慎回答，还是把证据转交给更专用的 Skill。

SECTION 06

Mining Pipeline 技术参考

与 Section 4 的叙事视角不同，本节从系统架构角度审视每个阶段的技术选型、当前代码落地情况与后续工业级增强方向。

分工说明：Section 4 "数据旅程" 用真实文档演示"发生了什么"；本节解释"为什么这样设计"以及"底层怎么实现"。
#阶段技术要点v1.2 增强方向
1parse 多格式解析入口：当前稳定解析的是 Markdown / PlainText，输出统一的 SectionNode 树，保留 heading 层级、table 列结构、list 编号。
HTML/PDF/DOC/DOCX 已进入 ingest 识别，但正文解析尚未完全收口		 下一步 补齐 HTML / DOCX / PDF 正文解析与统一结构输出
2segment 语义感知分段：每个 heading 独立成段；段落按 block_type（9 种）和 semantic_role（11 种）分类。
保留 section_path（JSON 路径数组）支持溯源到文档层级		 v1.2 语义分块：基于 embedding 相似度断点自动切分长段落
3enrich 规则 + 可选 LLM 增强：RuleBasedEntityExtractor、role classifier、table metadata 解析已经在主链中；当前代码也支持可选的 LLM enrich 持续增强 提高 batch 质量控制，并把 LLM 结果更正式地纳入发布质量门
4build_relations 结构关系为主，可选语篇增强：previous / next / same_section / section_header_of 已落地；代码中已接入可选 discourse relation builder 增强方向 让 discourse relation 从“可选增强”演进为更稳定的高质量资产层
5build_retrieval_units 多载体检索单元：当前主链已生成 raw_text、entity_card、table_row、generated_question；可选 contextual retrieval 会增强 search_text 增强方向 把 unit budget、质量门与召回收益评估更正式接入 build / release
6select_snapshot 共享快照模型：归一化策略（CRLF→LF → 去空白 → SHA256），document + snapshot + link 三层提交
内容寻址去重：相同内容的文档共享同一 snapshot		 v1.2 UPDATE 场景下旧 segments 自动清理
7assemble_build 知识视图组装：对比新旧快照 → 标记 NEW / UPDATE / SKIP / REMOVE，支持 full 和 incremental 两种构建模式 当前已落地 下一步重点从“能组装”转向“组装结果的质量分级”
8validate_build 当前仍以结构校验为主：非空检查、基本完整性、validation 结果记录；run_data_quality_eval() 已存在，但还不是正式 release gate 关键缺口 让数据质量校验进入正式发布门
9publish_release 版本发布：创建 release → 激活 → 旧版本退役。同一 channel 只有一个 active release，Serving 只读 active release 下一步 更强的 channel 治理、质量等级与回滚运营能力

Agent 如何真正使用 KnowledgeBase

阶段Agent 动作KnowledgeBase 输出
1. 识别是否需要证据 Agent 先判断当前问题是不是云核心网知识问题，而不是纯润色、翻译或通用推理。 决定是否调用 POST /api/v1/search，并带上 domain="cloud_core_network"。
2. 拉取证据包 Agent 把用户原问题交给 Serving，而不是自己先脑补答案。 返回 query、items、relations、sources、issues、suggestions 等结构化 Evidence Pack。
3. 做两个内部判断 Agent 必须形成 evidence_sufficiency 和 recommended_action 两个判断，而不是拿到片段就直接回答。 KnowledgeBase 通过 evidence_role、semantic_role、关系图和溯源信息支持这两个判断。
4. 选择动作 根据证据充足度，选择 answer_now / ask_followup / answer_with_caution / delegate_to_other_skill。 KnowledgeBase 不替 Agent 做最终决策，但把决策所需的证据和缺口显式暴露出来。
5. 把证据带入下游 若进入配置生成、故障分析、命令解释等专用 Skill，Agent 要把直接证据、支撑证据和缺口一起交过去。 Serving 输出的不是“答案”，而是可流转、可审计、可复用的证据包。
关键使用原则：先取证，再回答；证据不足时先追问；推理必须受证据约束。KnowledgeBase 的目标不是让 Agent 少思考，而是让 Agent 的思考建立在可溯源、可审计、可交接的证据之上。
Serving 铁律：不直接扫全库，不读取 mining_runtime，不绕过 Release 边界。所有读取必须从 Active Release → Build → Snapshots 开始。这是保证读一致性的核心约束。当前真正稳定的价值不只是“能搜”，而是“只消费已发布知识视图”。
SECTION 08

LLM Runtime — 统一智能增强层

独立 FastAPI 服务（端口 8900），统一管理所有 LLM 调用。Mining 和 Serving 不直接调用模型，而是通过这个独立运行时获取同步或异步能力。当前已形成稳定底座，但仍在持续工业化收敛。

核心能力

  • 双模式调用：Mining 异步 submit（批量），Serving 同步 execute（在线）
  • 模板系统：string.Template + JSON Schema 输出校验，模板版本化管理
  • 任务生命周期：queued → running → succeeded / dead_letter，自动重试
  • 幂等控制：idempotency_key 防重复提交
  • 全链路审计：task / request / attempt / result / event 完整链路可回溯
  • 多 Provider：chat provider 与 embedding/rerank provider 分层抽象，可扩展

API 端点一览

方法路径功能
POST/api/v1/tasks异步提交任务
POST/api/v1/execute同步执行（等结果）
GET/api/v1/tasks/{id}查询任务详情
GET/api/v1/tasks/{id}/result获取解析结果
GET/api/v1/tasks/{id}/attempts查看所有尝试
POST/api/v1/tasks/{id}/cancel取消任务
POST/api/v1/models/embeddings同步 embedding
POST/api/v1/models/rerank同步 rerank
GET/dashboardWeb 监控看板
场景调用方式代码示例
Mining 批量异步 submit → 轮询 get_result 
task_id = llm.submit(
    caller_domain="mining", pipeline_stage="enrich",
    template_key="entity_extract",
    input={"text": segment.raw_text})
# ... 处理其他文档 ...
result = llm.get_result(task_id)
Serving 同步在线 execute → 直接返回结果 
result = llm.execute(
    caller_domain="serving", pipeline_stage="planner",
    template_key="query_plan",
    input={"query": user_query})
当前实现口径：LLM Runtime 使用独立 SQLite WAL 任务面保存队列和审计数据；同步路径用于在线调用，异步路径用于批量增强。下一步重点不是再堆 endpoint，而是继续加强模板治理、Provider 运营能力和 SLA 监控。

SECTION 10

v1.2 目标态 — 知识自主演化

从"被动知识库"演进为"主动知识生态"。五大架构创新，让知识体系能够自我积累、自我校正、自我演进。

核心愿景：v1.1 解决了"如何把文档变成可检索的知识"。v1.2 要解决"如何让知识体系持续演化——自动积累高质量内容、淘汰过时内容、检测矛盾内容、理解段间深层语义"。

最终使用形态：Knowledge Skill Protocol

最终不是“Agent 直接把问题扔给一个搜索接口”，而是形成一套稳定的 Skill 协议：KnowledgeBase 负责产出证据包，Agent 负责基于证据做动作选择，专用 Skill 负责执行更窄、更深的领域工作。

层级职责目标态要求
KnowledgeBase 理解查询、检索证据、返回结构化 Evidence Pack、暴露缺口与建议追问。 证据角色、质量提示、scope 约束、relations、sources 全部标准化。
Agent Orchestrator 判断证据是否足够，决定是回答、追问、谨慎回答，还是转交其他 Skill。 形成统一的 evidence_sufficiency / recommended_action 决策协议。
Domain Skill 消费证据包，执行配置解释、排障分析、影响判断、命令生成等更具体任务。 所有高风险输出都必须绑定到上游证据，而不是脱离证据自由生成。

创新一：五层本体模型

传统知识库使用扁平本体（实体→属性），无法区分不同认知层次的知识。我们设计了五层递进结构：

L1 概念层
可配置对象
接口、协议、策略、VPN
→
L2 机制层
协议算法
事物如何工作
→
L3 方法层
操作程序
怎么配置、怎么排障
→
L4 条件层
决策规则
什么场景用什么方案
→
L5 场景层
业务场景
实际部署上下文
为什么五层：不同角色需要不同粒度的知识。集成工程师关注"怎么配"（方法+场景），方案设计师关注"什么条件下选什么方案"（条件+机制），架构师关注"概念间的关系"。扁平本体把这四类知识混在一起，查询粒度无法控制。

创新二：双层图架构

传统做法把事实直接连到知识图谱节点，导致图既用于推理又用于溯源，互相干扰。我们创新性地采用双层分离：

推理层 — 本体图

节点间只有语义关系边（DEPENDS_ON、EXPLAINS 等）。这些边是多条事实蒸馏后的聚合结论。

  • 3 条事实只产生 1 条边 → 图保持简洁
  • 支持依赖闭包、影响传播、跨层推理

溯源层 — 证据链

Fact → Evidence → Segment → Document 的完整证据链，回答"这个结论从哪来"。

  • 事实不直接连到本体节点（无 ABOUT_SUBJECT 边）
  • 事实生命周期管理完全独立
  • 推理查询只走推理层，溯源查询只走溯源层

创新三：声明式查询引擎

传统知识库要么只支持关键词搜索，要么需要复杂编程。我们设计了 5 个代数原语，用户只需表达"要什么"，规划器自动优化执行路径：

原语功能示例
seed初始化结果集按 ID / 别名 / 层级 / embedding / 属性匹配
expand图遍历沿本体边扩展，支持 tagged_in / rst_adjacent / evidenced_by
combine集合操作union / intersect / subtract
aggregate聚合排序分组、评分、关键词相关性、可选 Cross-Encoder 重排
project字段投影选择输出字段，组装最终 ContextPack
自动并行：规划器检测步骤间的变量依赖，将无依赖步骤编组为并行执行波，总查询超时 30s。

创新四：知识自治演化 — Auto-Promote 机制

知识体系不是静态的，而是持续自我改进的。通过三层候选词治理 + 自动晋升门控实现"知识的自然选择"：

Stage 3 文档级：每文档 LLM 分类 + 停用词过滤 + 初始评分 → 产出候选词
Stage 3b 循环级：基于累积 source_count 轻量重评分 → 高频词得分上升
Maintenance 日级：embedding 聚类去重 + LLM 批量分类 + 人工终审 → 最终确认
Auto-Promote 门控：当候选词满足 score ≥ 0.85 + 所有门控通过 + 存在 ≥7 天 → 自动晋升到本体。高质量知识自动积累，低质量被淘汰。

创新五：五维置信度评分

每条知识都有量化可信度评估，不是简单的"相关度分数"，而是五个维度的加权综合：

维度权重说明
source_authority 来源权威度0.30电信领域来源质量差距巨大（3GPP 规范 vs 论坛帖子），权重最高
extraction_method 提取方法0.20专门设计的规则（0.85）比通用 LLM（0.70）更可靠
ontology_fit 本体契合度0.20与已有本体结构的匹配程度，防止漂移
cross_source_consistency 跨源一致性0.20多个来源是否一致，冲突内容降分
temporal_validity 时效性0.10过时内容随时间自然衰减
v1.2 技术栈总览：五层本体 + 双层图 + 声明式查询 + 自治演化 + 五维置信度 + 语篇关系感知分段 + 父子层级检索 + 上下文增强 + BGE-M3 中文 embedding + jieba 分词。这不是功能的堆砌，而是一套互相增强的完整体系。
