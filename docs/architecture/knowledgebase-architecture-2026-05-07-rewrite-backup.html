2026 ARCHITECTURE UPDATE

KnowledgeBase 是一套面向 Agent 的知识生产、知识发布与智能增强底座

当前系统已经从早期单体式“文档检索思路”演进为三条独立但协同的主链：Mining 负责把原始文档转成可发布知识资产，Serving 负责把在线问题转成可消费的证据包，LLM Runtime 负责提供统一的模板化智能能力、异步队列与审计链路。对外汇报时，KnowledgeBase 不再强调单一演示链路，而强调可持续演进的系统骨架。

这次更新的口径

文档内容以仓库当前实现为基础重写，不再延续旧版架构文档中“目标态堆叠”的写法。系统名称统一为 KnowledgeBase，整体架构图只保留三大角色之间的交互，不再展开到单个算法节点级别。

SECTION 01

系统定位

KnowledgeBase 不是单纯的文档搜索服务，而是把知识的“生产”“发布”“消费”拆成可独立治理的三个运行面。

Mining

从文档目录出发，完成摄取、结构解析、分段、增强、关系构建、检索单元生成、Build/Release 发布。

Serving

从在线查询出发，完成问题理解、路由规划、多路召回、融合、重排、ContextPack 组装，面向 Agent 返回可执行证据包。

LLM Runtime

作为共享智能能力层，提供模板注册、同步执行、异步队列、幂等、租约恢复、审计链路和 Provider 抽象。

核心设计原则：Mining 负责写知识资产，Serving 只消费已发布资产，LLM Runtime 提供跨系统复用的智能执行合同。三者边界清晰，便于独立演进与独立治理。

  • 统一模板、Provider、重试、审计

当前真实交互

1
Mining 将文档加工结果写入 PostgreSQL 知识面中的 asset_core，并通过 build/release 选择一组对外可见的快照。
2
Serving 查询时先解析 active release，再在 active snapshots 范围内执行 BM25、实体召回、向量召回、扩展与组装。
3
Mining 与 Serving 都可调用 LLM Runtime，但两者调用模式不同：Mining 偏异步批处理，Serving 偏同步在线增强。

对外汇报时的表达重点

A
先强调 “知识生产” 与 “知识消费” 的严格分离，而不是先讲单个算法。
B
再强调 Serving 消费的是经过发布控制的知识视图，而不是任意运行中的中间结果。
C
最后强调 LLM 只是统一增强能力，不侵入知识主存模型，从而保留可替换性与审计能力。
SECTION 03

Serving 当前实现

Serving 已经从早期单路检索演进为可运行的检索编排器，主入口是 FastAPI 的 /api/v1/search，当前代码位于 agent_serving/serving，运行时基于 PostgreSQL、pgvector 与 llm_service 组合。

当前主链

1
加载领域配置与请求参数，进行 query understanding，输出意图、关键词、实体、scope 与 evidence need。
2
生成 retrieval route plan，按意图选择 lexical_bm25、entity_exact、dense_vector 等 route。
3
解析当前 active release 和 active snapshots，在只读范围内执行多路召回、融合与重排。
4
下钻 source segment、做 relation expansion，并组装为面向 Agent 的 ContextPack。

当前已落地的能力

  • API 主入口：/api/v1/search，并具备 /health 健康检查。
  • 理解层：LLM-first + rule fallback 的 query understanding。
  • 召回层：BM25、向量召回、图扩展已接入主链；实体 route 已有实现基础，但仍在收口。
  • 排序层：identity/RRF/weighted RRF 融合，级联 rerank。
  • 输出层：带 citation、route trace、debug trace 的 ContextPack。
实现面 当前代码口径 状态
运行边界 Serving 不写知识资产，只解析 active release 后读取 PostgreSQL 中的 asset_core 资产，并按 route 决定是否调用 embedding 与 LLM。 已稳定成型
接口合同 SearchRequest、QueryUnderstanding、RetrievalRoutePlan、ContextPack 等模型已在 serving/schemas/models.py 固化。 已落地
召回策略 多路并发召回已建立，BM25 依赖 PostgreSQL 文本检索，dense 依赖 pgvector；但 filter/scope 仍未深度下推到各 route 的 SQL 或索引策略中。 持续收敛
工业化缺口 向量召回仍偏 brute-force，实体召回仍偏 JSON/LIKE 过渡方案，线上 trace 还没有持久化指标系统。 下一阶段
汇报口径建议：Serving 当前最值得强调的，不是“又加了一种检索算法”，而是已经具备了“只消费已发布知识视图的在线编排骨架”。这意味着后续的语义检索、实体索引、重排优化都可以在稳定边界内演进。
SECTION 04

Mining 当前实现

Mining 当前代码位于 knowledge_mining/mining，主执行入口是 jobs/run.py。它负责把原始文档加工成可发布知识资产，并在 PostgreSQL 知识面上维护 build/release 生命周期。

当前主链

1
摄取输入目录，识别 md/txt/html/pdf/doc/docx，并计算原始哈希与归一化哈希。
2
对已支持格式做 parse 与 segment，再执行 enrich、relations、retrieval units 与 embedding 写入。
3
通过 shared snapshot 模型复用内容快照，并把文档状态归类为 NEW/UPDATE/SKIP/REMOVE。
4
组装 build、校验 build、创建并激活 release，使下游 Serving 获得稳定读取视图。

当前已落地的能力

  • 双表族分离：asset_core 负责知识资产，mining_runtime 负责运行态记录，当前都落在同一 PostgreSQL 数据面中。
  • 共享快照：document / snapshot / link 三层模型已落地。
  • 关系层：结构关系、reference relation、可选 discourse relation。
  • 检索层资产：raw_text、entity_card、table_row、generated_question。
  • 发布层：build/release 生命周期与增量继承逻辑已建立。
实现面 当前代码口径 状态
数据主模型 Build/Release、共享快照、运行态记录和检索资产层都已在主链中真实使用，不再是设计占位。 已落地
解析能力 当前真正稳定支持的是 markdown / txt；html/pdf/doc/docx 已进入 ingest 识别，但正文解析仍未收口为生产能力。 部分完成
质量治理 已有 run_data_quality_eval() 等旁路能力，但 validate_build 仍以结构校验为主，尚未成为正式 release gate。 待提升
工业化缺口 运行真相源、自动 resume、领域合同收口、内容质量发布门仍需继续加固，才能形成强约束的知识生产平台。 下一阶段
汇报口径建议：Mining 当前最值得强调的是“知识资产发布面已经建立”，而不是把所有增强能力都描述成已经工业化完成。对外更合适的表述是：底座已成型，质量门与跨格式能力仍在收口。
SECTION 05

LLM Runtime 当前实现

LLM Runtime 当前代码位于 llm_service，是一个独立 FastAPI 服务，用统一合同承接 Mining 和 Serving 的智能调用需求，并以 SQLite WAL 维护自己的任务与审计存储。

当前主链

1
模板通过 /api/v1/templates 注册，支持 string.Template 变量替换与 JSON Schema 约束。
2
Serving 走同步 /api/v1/execute，直接等待结果；Mining 走异步 /api/v1/tasks，由 Worker 后台执行。
3
任务进入 SQLite WAL 队列，受幂等、优先级、租约、重试与恢复逻辑管理。
4
所有调用沉淀为 task / request / attempt / result / event 审计链，并暴露结果查询与 dashboard。

当前已落地的能力

  • 双模式接口：/api/v1/execute 与 /api/v1/tasks。
  • 扩展接口：/api/v1/models/embeddings 与 /api/v1/models/rerank。
  • 模板生命周期：创建、查询、更新、归档。
  • 运行控制：幂等键、lease recovery、指数退避重试、任务取消。
  • 可观测性：事件流水、attempt 明细、dashboard 页面与统计接口。
实现面 当前代码口径 状态
服务边界 LLM Runtime 已独立于 Mining/Serving 业务代码，统一承接模板化 LLM、embedding、rerank 能力。 已落地
执行模型 同步执行与后台 Worker 并存，且具备 lease recovery 和幂等控制，已经形成可靠的基础调度骨架。 已成型
审计能力 任务、请求、尝试、结果、事件五段链路可回溯单次调用输入输出、耗时、tokens 与错误。 已落地
工业化缺口 后续重点不在“再做一个 endpoint”，而在更强的模板治理、Provider 运营能力、SLA 监控与多实例部署策略。 下一阶段
汇报口径建议：LLM Runtime 当前已经可以被描述为一个独立的“智能执行底座”，而不是散落在业务代码中的若干模型调用。它是 KnowledgeBase 未来横向扩展的重要支点。
SECTION 06

三部分共享的底座能力

KnowledgeBase 的可扩展性不来自单个大模型或单个检索器，而来自清晰的数据边界、发布边界和调用边界。

发布边界

Mining 决定哪些 snapshot 进入 build，哪个 release 变成 active。Serving 永远消费“被发布”的 PostgreSQL 知识视图，而不是消费任意运行中的临时结果。

智能边界

LLM Runtime 统一承接模板、队列、Provider、审计，使 Mining 与 Serving 不需要各自维护独立的智能执行基础设施。

领域边界

两端都已经引入 Domain Pack 概念，但共享合同还需要继续收口，这是从“单项目知识系统”走向“通用知识平台”的关键步骤。

共享能力 当前状态 意义
Shared Snapshot 已用于去重与 build 继承，避免同一内容重复存储。 成本与一致性
Build / Release 已形成生产知识与消费知识之间的中介层。 隔离读写路径
Domain Pack Mining 与 Serving 都有领域配置入口，但当前仍未完全统一为单一共享 schema。 平台化关键
质量门 局部已具备 eval、trace 与审计，但尚未全部成为 release / routing 的强门禁。 工业化关键
当前数据面口径：Mining 与 Serving 当前共享的是 PostgreSQL 知识数据面；LLM Runtime 维持独立的 SQLite 任务与审计数据面。这样既保证知识主链的一致性，也保证智能调用层可以独立演进。
SECTION 07

从当前实现走向工业级目标

KnowledgeBase 的下一阶段，不是推翻现有架构，而是在现有三部分边界之上，把质量约束、可扩展性与运营能力继续做硬。

方向 当前基线 工业级目标
Mining 质量治理 build validate 仍以结构正确性为主。 把 data quality eval、unit budget、内容污染检查正式接入 release gate。
Serving 可扩检索 已有多路编排，但 dense/entity 路径仍偏过渡实现。 升级为可扩向量检索、正式实体索引、可观测 route policy 与更强线上评估闭环。
LLM Runtime 运营能力 已具备模板、队列、审计、恢复。 继续加强模板治理、多 Provider 策略、性能监控、SLA 与横向部署能力。
共享领域合同 两端各自可读 Domain Pack。 收口为统一 schema 和统一运行时对象，减少双端口径漂移。
平台发布治理 active release 已建立，但质量等级还不够显式。 引入质量分级、channel 策略、灰度与回滚机制，把发布控制从“可发布”提升为“可运营”。

当前应该向外界传达的结论

  • KnowledgeBase 已经形成 Mining / Serving / LLM Runtime 三部分独立协同的系统骨架。
  • 知识生产与知识消费已经通过 build/release 边界解耦。
  • LLM 能力已经抽离为独立运行时，而不是业务代码里的临时调用。

当前不宜夸大的部分

  • 不要把所有解析格式都表述成已经工业化完成。
  • 不要把所有质量评估都表述成已经成为发布门。
  • 不要把当前检索增强层表述成已经完成大规模运营级优化。
